\section{Product Overview}
\subsection{Vision}
FashionOS runs the client's whole fashion business from one system: billing at the shop, selling on the website, tracking one shared stock, handling customer credit (khata) with WhatsApp bills, paying staff and fall-pico workers, and keeping Tally books correct, with AI helping customers shop and the owner decide what to buy.

\subsection{Goals}
\begin{enumerate}
\item One stock for shop and website, so nothing is oversold and nobody counts twice.
\item Fast shop billing that keeps working when the internet is down.
\item Khata customers get an instant WhatsApp bill and can pay from home; the owner always knows who owes what.
\item Tally always matches FashionOS, without double entry by the accountant.
\item Staff salary, advances and fall-pico worker payments are clear and disputes are rare.
\item AI increases sales (recommendations, search, chat, posters) and improves buying decisions (trends, demand, missing products).
\end{enumerate}

\subsection{Key Design Decisions}
\begin{enumerate}
\item \textbf{Modular monolith} for the backend. Simple for 5 people; modules can be split later.
\item \textbf{One stock ledger.} Every change to stock is a row in \code{stock_movements}; \code{stock_levels} is the current total. Shop, website, purchases, returns and Tally imports all write to it.
\item \textbf{Append-only money ledgers.} Khata, employee and worker balances are sums of entries. Entries are never edited or deleted; mistakes are fixed by reversing entries.
\item \textbf{Outbox pattern.} Anything that must reach Tally or WhatsApp is first saved in an outbox table in the same database transaction as the sale, then sent by a worker with retries. No sale is lost if Tally or WhatsApp is down.
\item \textbf{Offline-first POS.} The POS keeps its own copy of products, prices and customers, saves bills locally, and syncs when online. Each bill has a unique idempotency key, so a retry never creates a second bill.
\item \textbf{Tally agent is outbound only.} The agent runs on the same server as Tally and opens the connection to FashionOS. Tally's interface is never open to the internet.
\item \textbf{Tally is the master of books, FashionOS is the master of daily bills, stock and khata} (SRS 2.1). Conflicts go to a Sync Issues screen, never silently overwritten.
\item \textbf{AI is a separate service} with timeouts and fallbacks, so it can fail without stopping billing.
\item \textbf{Payments are confirmed only by gateway webhook}, never by the browser.
\item \textbf{Money is stored in paise} as whole numbers; GST is calculated on the server.
\item \textbf{Everything important is audited} (who, what, old, new, when, device).
\end{enumerate}

\subsection{Flow in Mode B (FashionOS POS): Khata Sale to WhatsApp and Tally}
\begin{enumerate}
\item Cashier scans items, picks the khata customer, chooses khata payment.
\item POS checks credit limit (using the last synced balance) and warns if crossed.
\item POS saves the bill locally and sends it to the API with its idempotency key.
\item API in one transaction: saves bill, deducts stock, adds a khata ledger entry, creates fall-pico jobs for eligible sarees, writes outbox rows for Tally and WhatsApp.
\item Message worker asks the AI service for wording, checks every number against the ledger, picks an approved template and sends on WhatsApp (SMS if it fails).
\item Tally worker hands the sales voucher to the sync agent; the agent posts it to Tally and reports back; the outbox row is marked done.
\item Later the customer pays through the Pay Now link: Razorpay webhook, ledger entry, WhatsApp receipt, Tally receipt voucher.
\end{enumerate}

\subsection{Flow in Mode A (counter bills in TallyPrime; first step of rollout)}
\begin{enumerate}
\item The cashier makes a khata bill in TallyPrime as today, with the customer's ledger as the party.
\item The sync agent on the Tally server reads the new voucher and sends it to the cloud (\code{/tally/inbox}).
\item The cloud matches the Tally party to a FashionOS customer (through \code{tally_ledger_map}), saves the sale (source \code{tally_import}), deducts stock and adds the khata ledger entry.
\item A WhatsApp job is created. Wording, validation and sending follow section 4.4. Delay: up to 5 minutes.
\item Saree lines above the fall-pico limit create fall-pico jobs.
\item Website stock is updated as soon as step 3 is done.
\item When the customer pays through the Pay Now link, FashionOS records the payment, sends the WhatsApp receipt, and the agent posts a Receipt voucher to Tally.
\item If the party or an item cannot be matched, the bill goes to the Sync Issues screen and no message is sent.
\end{enumerate}

\section{Module Technical Notes}
\subsection{Shared Stock and Reservations (FR-CAT-02..04)}
\code{stock_levels} holds \code{on_hand} and \code{reserved} per variant. A variant is sellable when \code{on_hand - reserved >= quantity}.
\begin{itemize}
\item Shop bill: deduct \code{on_hand}. Online order: add to \code{reserved} until paid, then deduct; release on cancel or after 30 minutes unpaid.
\item Updates use one atomic statement or a row lock inside a transaction, so the last unit can only be sold once.
\item \textbf{Offline POS case:} a counter without internet may sell a unit that was sold online in the meantime. The sync accepts the bill (it already happened), stock goes negative, and the owner gets a Stock Conflict alert. \assump{} Accept and alert, never reject a finished shop sale.
\item Stock count mode writes adjustment movements with a reason; nothing overwrites \code{on_hand} directly.
\end{itemize}

\subsection{Offline POS (FR-POS-08)}
\begin{itemize}
\item POS is an installable web app (PWA). A service worker caches the app; IndexedDB stores products, prices, barcodes, khata customers (with last synced balance and time), the bill queue and settings.
\item Each counter has its own bill number series (for example \code{C1-26-000123}). The bill number plus counter ID is the idempotency key sent to the API.
\item Sync runs every few seconds when online: send queued bills in order, then pull changes since the last sync token. Failed bills stay in the queue and are shown to the cashier.
\item Credit limit check offline uses the cached balance and shows ``balance may be outdated''. The owner can set a safer limit for offline mode.
\item Printing: browser print for A4; a small local print helper or ESC/POS over USB/network for thermal printers \todo{TBD by printer model}.
\item Day-close needs all queued bills synced, or shows what is missing.
\end{itemize}

\subsection{Khata Ledger (FR-KHT)}
Table \code{ledger_entries} (append-only): \code{account_id}, \code{type} (SALE, PAYMENT, RETURN, ADJUSTMENT, WRITE\_OFF, REVERSAL), \code{amount_paise} (positive = customer owes more), \code{ref_type}, \code{ref_id}, \code{note}, \code{created_by}, \code{running_balance_paise}.
\begin{itemize}
\item Writing an entry locks the account row, reads the last balance, writes the new balance. This keeps the running balance correct when two entries arrive together.
\item Payments are allocated oldest bill first (\code{ledger_allocations}), so ageing is accurate.
\item A reversal entry points to the entry it cancels; both stay visible.
\item Daily integrity job: recompute every balance from entries and compare. Any difference raises an alert (NFR-DATA-01).
\item Reminder rules (days after bill, due date, weekly) run as a scheduled job and respect quiet hours, opt-out and disputes.
\end{itemize}

\subsection{WhatsApp Pipeline (FR-WAP)}
\begin{enumerate}
\item Event (khata sale, payment, reminder, fall-pico ready) creates a \code{message_jobs} row with the facts needed (amounts, dates, bill number, balance).
\item The message builder calls the AI service with placeholders (for example \texttt{\{amount\}}, \texttt{\{new\_balance\}}), the customer's language and tone, and asks only for wording.
\item The validator fills the placeholders from the database and checks that no other number appears in the text. If the check fails, the standard template is used.
\item The sender picks an approved template (or free text inside the 24-hour window) and calls the provider API.
\item Provider webhooks update status: sent, delivered, read, failed. A failure triggers SMS and flags the ledger entry.
\end{enumerate}
Tables: \code{message_templates} (name, language, approval status), \code{whatsapp_optins}, \code{message_jobs}, \code{message_events}. Template names and wording are submitted to Meta in Phase 0; approval can take days.

\subsection{Online Payments and Pay Now Links (FR-PAY, FR-PRT)}
\begin{itemize}
\item Website checkout: create order (\code{PENDING_PAYMENT}), create Razorpay order, customer pays, webhook with verified signature marks it paid. Idempotency by gateway payment ID.
\item Pay Now: a signed, unguessable token for one customer, valid 7 days, rate limited. It opens a page with balance and recent bills; paying creates a Razorpay payment for the chosen amount.
\item On webhook: write a PAYMENT ledger entry, allocate to oldest bills, queue WhatsApp receipt and Tally receipt voucher. Duplicate webhooks do nothing.
\item Overpayment becomes advance credit on the ledger.
\end{itemize}

\subsection{Tally Integration (FR-TLY)}
Parts: the outbox in the cloud, the sync agent on the Tally server, and mapping tables. TallyPrime runs on a cloud Windows server in India, on 24 hours (client decision; hosting and licence to confirm). The agent runs on that same server.
\begin{itemize}
\item \textbf{Two modes (SRS 3.18).} Mode A: the counter bills in TallyPrime and FashionOS imports the bills. Mode B: the counter bills in the FashionOS POS and FashionOS pushes sales to Tally. A \code{tally_mode} setting with a cutover date decides; only one mode is active, so a sale is never entered twice.
\item \textbf{Tally to FashionOS} (Mode A, and always for purchases or stock entered in Tally): the agent reads new or changed vouchers and stock using Tally's change counter \todo{verify for the latest TallyPrime} and sends the raw vouchers to \code{tally_inbox}. The cloud turns them into sales, returns, purchases and stock movements marked \code{tally_import}, and skips anything it created itself.
\item \textbf{FashionOS to Tally:} the agent asks the cloud for pending outbox items over HTTPS, builds the Tally XML, posts it to Tally on the same server, then confirms success or error. Always sent: online orders, Pay Now receipts, shop receipts, supplier payments. In Mode B also shop sales and returns. Each voucher carries a unique FashionOS reference so a retry cannot create a second voucher.
\item \textbf{Mapping tables:} \code{tally_item_map} (variant to stock item), \code{tally_ledger_map} (customer ledger name to phone; supplier, employee, GST, sales, cash, UPI and bank ledgers), \code{tally_voucher_types}.
\item \textbf{Voucher types used:} Sales, Credit Note (returns), Receipt, Purchase, Debit Note, Payment, and Journal when needed.
\item \textbf{Availability:} the server is on 24 hours. A setting holds Tally's working hours (default 24 hours; 11 am to 9 pm only if Tally stays on the shop computer). If Tally cannot be reached, items wait and retry with backoff; the alert goes out after 30 minutes inside working hours. A backlog clears within 15 minutes of Tally opening, and every voucher keeps its original date and time.
\item \textbf{Errors} (missing ledger, locked period, unknown party or item) go to the Sync Issues screen with the reason. In Mode A a khata bill with an unmatched party sends no WhatsApp message.
\item \textbf{Reconciliation:} a nightly job (and again after opening) compares day totals (sales, GST, receipts) and item stock between FashionOS and Tally and lists differences.
\item \textbf{Bill numbers:} in Mode A numbers come from Tally. In Mode B FashionOS uses a new series from \code{bill_series} (prefix, financial year, counter, running number), unique and in order, designed with the accountant under GST rules. The old series stays closed in Tally.
\item \textbf{Security:} the agent has its own API key and makes outbound HTTPS calls only. Tally's local interface is never open to the internet. The server is in India, open to named users (two-factor where the host offers it), with a daily backup of company data kept apart from the server.
\item \textbf{Internet dependency:} while the counter bills in cloud Tally (Mode A), billing needs the internet. Keep a backup connection or the paper bill book (FR-TLY-27). This ends at cutover, because the POS works offline.
\item \textbf{Go-live import:} items, ledgers and opening balances are read from Tally once and checked by the accountant, after a data quality check on a sample.
\end{itemize}
\textbf{Verify in Sprint 0:} the exact latest TallyPrime version on the server, whether the agent can run next to it, which requests are supported, and the licence for several users.

\subsection{Employees and Payroll (FR-EMP)}
\begin{lstlisting}
Payable days = Present + Half-day x 0.5 + Paid leave + Weekly off (as per shop rule)
Monthly staff: Earned = Monthly salary x Payable days / Days in month
Daily staff:   Earned = Daily rate x Payable days
Gross          = Earned + Incentive + Overtime
Net payable    = Gross - Advance recovery - Other deductions
Pending        = Net payable - Salary already paid this month
\end{lstlisting}
\textbf{Example:} salary 15,000, 30-day month, 24 payable days, earned 12,000; advance recovery 1,000; net 11,000; already paid 6,000; pending 5,000. Advance of 5,000 falls to 4,000.
\begin{itemize}
\item Tables: \code{employees}, \code{attendance}, \code{salary_runs}, \code{salary_lines}, \code{advances}, \code{advance_recoveries}, \code{salary_payments}. All money tables are append-only with reversals.
\item A salary run is a draft until the owner approves; after approval it is locked.
\item Salary screens and APIs are allowed only for Owner, Accountant and the employee (own record).
\end{itemize}

\subsection{Fall-Pico (FR-FPC)}
\begin{itemize}
\item \textbf{Job states:} PENDING $\rightarrow$ ASSIGNED $\rightarrow$ IN\_PROGRESS $\rightarrow$ COMPLETED $\rightarrow$ QC\_PASSED $\rightarrow$ READY $\rightarrow$ HANDED\_OVER. Side paths: REWORK (from QC fail), CANCELLED.
\item On bill or paid order, for each saree line with \code{fall_pico_eligible = true} and price above the limit (setting, default 1,000), create one job and print the tag. The customer can decline at the counter; online customers can skip at checkout.
\item Assignment: manual or lowest open jobs. Capacity per worker is a soft limit.
\item \code{fp_job_events} records every handover and return (who, when, state), so a saree can always be found.
\item \textbf{Wages:} a job becomes payable when it reaches QC\_PASSED. Wage = worker rate at that time $\times$ number of pieces. Rework is not paid again. Worker statement: jobs done, earned, paid, advance, balance (same ledger design as employees).
\item \textbf{Online orders:} after payment the order enters FALL\_PICO\_IN\_PROGRESS; it can be packed only when the job is QC\_PASSED or skipped.
\item \textbf{Cost:} monthly cost = wages + material; report cost per saree.
\end{itemize}

\subsection{Relationships (simple view)}
\begin{itemize}
\item A customer has many bills, orders and addresses, and at most one khata account, which has many ledger entries.
\item A bill or order has many items; a saree item can create a fall-pico job, which has events, one worker and a wage entry.
\item A variant has one stock level and many stock movements from bills, orders, purchases, returns and Tally imports.

\item Every bill, payment, return, purchase, salary and wage can have outbox rows for Tally.

\subsection{Database Rules}
\begin{itemize}
\item UUID primary keys; \code{created_at}, \code{updated_at}, \code{created_by} on every table; \code{tenant_id} is not needed (single business).
\item Money in paise (integers). Dates in UTC, shown in IST.
\item Financial and stock tables are append-only: no update or delete; reversals only.
\item Products and customers use soft delete.
\item Unique constraints on bill number per counter, voucher reference, gateway payment ID and idempotency keys.
\item Indexes on \code{bills(created_at)}, \code{ledger_entries(account_id, created_at)}, \code{stock_movements(variant_id, created_at)}, \code{tally_outbox(status, created_at)}, \code{fp_jobs(status, worker_id)}.
\item Migrations through a tool; no manual edits in staging or production. Row-level access checks for salary and khata data.
\end{itemize}
\textbf{Added in v1.0:} \code{bill_series} (prefix, financial year, counter, next number) holds the new bill numbering. Every bill and stock movement has a \code{source} (\code{pos}, \code{website}, \code{tally_import}) so Mode A and Mode B can be told apart. \code{tally_inbox} stores the raw vouchers read from Tally. A \code{tally_mode} setting (A or B) records the mode and the cutover date.

\subsection{Coding Standards}
\begin{itemize}
\item Backend and AI service: Python 3.11+ with type hints everywhere and Pydantic for all input and output. Web: TypeScript (strict). Tally agent: Python.
\item Format and lint: Ruff and Black (Python); ESLint and Prettier (web). Pre-commit hooks and CI enforce them.
\item Names: \code{snake_case} in Python and database columns; \code{camelCase} variables and \code{PascalCase} components in TypeScript; \code{kebab-case} folders and files in the web app.
\item Money is always an integer in paise, never a float (\code{app/core/money.py}, \code{src/lib/money.ts}).
\item Every API input is validated. No secrets or personal data in logs.
\item Anything that writes to stock, ledgers, salary or the outbox goes through a service function with one transaction and an audit entry. Routers never write to tables directly.
\item Every bill and every webhook uses an idempotency key.
\item Ledger, stock movement and audit tables are append-only, enforced by \code{database/policies}. Fix mistakes with a reversing entry.
\item Database changes only through Alembic migrations.
\item Comment the \emph{why}, not the \emph{what}.
\end{itemize}
